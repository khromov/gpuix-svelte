12 of the 16 nodes reach GPUI

Svelte's renderer API is shaped like the DOM, with comment anchors, fragments and whitespace between tags. GPUI's tree holds elements and text, keyed by number. The renderer keeps Svelte's tree in JavaScript, as a shadow tree, and creates native nodes only for elements and non-blank text, once they're attached to the window.

Multi-value shorthands expand

padding: 12px 24px arrives as four keys. A single value stays one key: .card's padding: 32px is "padding":32 in row 7.

Values GPUI can't use are dropped

A value GPUI can't parse would make applyBatch throw and lose the frame. The renderer drops it and warns once per property. These four warnings came from the styling playground, npm run demo:styling:

How a click reaches the screen

Everything runs in one Node or Bun process, with no DOM, webview or browser. JavaScript and Rust meet at the addon: events come in through one callback, and changes go out through applyBatch.

Loaders

The gpuix-svelte bin starts Node with a .svelte loader on module.registerHooks, or Bun with one on Bun.plugin. Components compile with Svelte's customRenderer option, so each imports gpuix-svelte/renderer.

Frame loop

A setTimeout loop at about 125 fps calls the addon's tick(). Changes made outside an event, by a timer or a fetch, ship from there.

Hot reload

render_hot watches the entry's folder and remounts the new component in the same window. Component state starts over, and state in a .svelte.ts module survives.

WebAssembly

GPUI compiled to WebAssembly takes the same applyBatch calls and paints a WebGPU canvas (WebGL2 as a fallback). The renderer code is unchanged, and no component becomes a DOM node.

Tests and automation

Tests mount components on GPUI's test renderer, with no window, and click through GPUI's real hit testing and input pipeline. They're plain scripts, with no test runner.

test.tsthe starter's test
import { mount_headless, click_test_id, all_text, check, finish } from 'gpuix-svelte/test';
import App from './App.svelte';

mount_headless(App, { width: 400, height: 300 });

click_test_id('plus');
click_test_id('plus');
click_test_id('minus');

check('the buttons reached the counter', all_text().includes('1'));
finish('starter', 1);
npm test
ok   the buttons reached the counter

starter ok

click_test_id('plus') finds the element by its testId and clicks its painted centre. Headless tests run on macOS and Windows; the Linux prebuild has no test renderer.

Driving a running app

gpuix-svelte/automation drives a running app's real window from another process, with a Playwright-style App and Locator. The wire is JSON over the app's stdin and stdout, so any language can drive it. test_app() runs the same script headlessly.

Testing docs→
drive.tsfrom the testing docs
import { launch } from 'gpuix-svelte/automation';

const app = await launch({ entry: 'src/main.ts' }); // bun: true runs the app on Bun
for (let i = 0; i < 3; i++) await app.getByTestId('plus').click();
await app.getByText('3 clicks').waitFor();
await app.screenshot({ path: '/tmp/counter.png' });
await app.close(); // ends the app's stdin; it answers what is in flight and exits 0

Quick start

bash
$ npm create gpuix-svelte@latest my-app
$ cd my-app
$ npm install
$ npm start

A counter opens in its own window. Edit App.svelte, save, and the window hot-reloads.

On Bun, run bun create gpuix-svelte my-app, then cd my-app, bun install and bun run start.
